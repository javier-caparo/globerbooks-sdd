# 📚 GloberBooks: Business Requirement Document (BRD) & SDD Workflow

## Part 1: Business Requirement Document (BRD)

### 1. Executive Summary

- The GloberBooks project is a pilot initiative designed to implement a robust, AI-assisted development workflow.
- Unlike traditional "vibe coding" (ad-hoc prompting), this project utilizes Spec-Driven Development (SDD) to build a personal reading list tracker.
- The primary goal is to maintain a "Human-in-the-Loop" (HITL) oversight model, ensuring that the AI agent (CODA) remains aligned with architectural guardrails and business logic.

### 2. Project Scope

- The scope includes the development of a lightweight RESTful API and a frontend to manage a collection of books.
- **In-Scope:** CRUD operations for books, status tracking (unread/reading/completed), and a rating system.
- **Out-of-Scope:** User authentication/multi-user support, persistent cloud databases (using local/in-memory storage instead), and third-party API integrations for book metadata.

### 3. Functional Requirements

The system must allow users to perform the following actions:

| ID | Requirement | Description |
|----|-------------|--------------|
| FR1 | Add Book | Users can add a book with: Title, Author, and Status. |
| FR2 | Track Status | Users can update a book's status to: unread, reading, or completed. |
| FR3 | Rate Books | Users can provide a numerical rating between 1 and 5. |
| FR4 | Author Bio | Users can store a brief biography/description for the author (added via Drift Management phase). |

### 4. Business Rules (The "Constitution")

The following rules are immutable and must be enforced by the Human-in-the-Loop during the development lifecycle:

- **Rating Integrity:** A rating can only be assigned if the book status is set to completed.
- **Validation Range:** Ratings must be an integer between 1 and 5 inclusive.
- **Data Integrity:** Duplicate book titles should be flagged or handled based on architect clarification.
- **Technical Guardrails:**
  - No hardcoded secrets or sensitive data.
  - Mandatory unit tests for all business logic.
  - Explicit error handling with standard HTTP status codes (e.g., 400 for bad ratings, 404 for missing books).

### 5. Architectural Approach

The project follows a tiered governance model to prevent "Context Drift":

- **The Constitution:** Defines the high-level "Laws of the Codebase" (Stack, ALWAYS/NEVER boundaries).
- **The Specification (spec.md):** The single source of truth for features and rules.
- **The Plan (plan.md):** The architectural blueprint generated by the AI and approved by the Human.
- **Task Decomposition (tasks.md):** Atomic, sequential steps to ensure the AI does not lose context.

### 6. Success Criteria

The project is considered successful if:

- The final codebase passes all unit tests defined in the implementation phase.
- The system successfully rejects ratings for books not marked as "completed".
- The development artifacts (constitution.md, spec.md, plan.md, tasks.md) are fully synchronized with the final code.
- The developer can demonstrate "Self-Healing" by reverting un-specced changes and updating the documentation before implementation.

### Phase 2: Defining Intent - The Specify Phase

**Estimated time:** 1.5 Hours.

**Goal:** Define WHAT the system should do and WHY, without prescribing HOW.

#### Tasks

**1. Create spec.md (40 min)**

Use this structured template:

```markdown
# GloberBooks Product Specification

## 1. Overview
**Problem Statement:** Readers need a simple way to track books they want to read, are reading, and have completed.
**Target Users:** Individual readers managing personal reading lists
**Success Metrics:**
- User can add a book in <10 seconds
- User can view their library instantly
- Zero data loss on app restart

## 2. User Stories

### US-001: Add Book
**As a** user
**I want** to add a book with title, author, and status
**So that** I can track my reading list

**Acceptance Criteria:**
- Title is required (1-500 chars)
- Author is required (1-200 chars)
- Status is optional, defaults to "unread"
- Valid statuses: unread, reading, completed
- System assigns unique ID and timestamp

### US-002: List Books
**As a** user
**I want** to see all my books in a list
**So that** I can review my reading progress

**Acceptance Criteria:**
- Shows all books sorted by date added (newest first)
- Displays title, author, status, rating (if completed)
- Option to filter by status
- Empty state message if no books

### US-003: Rate Completed Books
**As a** user
**I want** to rate books I've completed
**So that** I can remember which ones I enjoyed

**Acceptance Criteria:**
- Rating only allowed for "completed" books
- Rating is 1-5 (integers only)
- Rating is optional (can be null)
- Can edit rating after initial assignment

### US-004: Prevent Duplicate Books
**As a** user
**I want** to be warned about duplicate books
**So that** I don't accidentally add the same book twice

**Acceptance Criteria:**
- Compare title + author (case-insensitive, trimmed)
- Show confirmation dialog if match found
- User can override and add anyway (for different editions)

## 3. Business Rules

### BR-001: Status Validation
**Given** a user sets book status
**When** the status value is provided
**Then** it must be one of: unread, reading, completed
**And** invalid values return error code `INVALID_STATUS`

### BR-002: Rating Validation
**Given** a book with status "completed"
**When** a user assigns a rating
**Then** system accepts integers 1-5 (inclusive)
**And** rejects other values with error code `INVALID_RATING`

**Given** a book with status "unread" or "reading"
**When** a user attempts to assign a rating
**Then** system rejects with error code `RATING_NOT_ALLOWED`

### BR-003: Duplicate Detection
**Given** a book with title "Clean Code" and author "Robert Martin" exists
**When** user adds book with same title and author (case-insensitive)
**Then** system prompts: "This book may already exist. Add anyway?"
**And** user can confirm or cancel

## 4. Data Model (Conceptual)

### Book Entity
- `id`: string (UUID, system-generated)
- `title`: string (required, 1-500 chars)
- `author`: string (required, 1-200 chars)
- `status`: enum (unread | reading | completed, default: unread)
- `rating`: integer (1-5, nullable, only for completed books)
- `date_added`: timestamp (system-generated)
- `date_completed`: timestamp (nullable, set when status changes to completed)

## 5. API Contract

### GET /api/v1/books
**Purpose:** Retrieve all books
**Query Parameters:**
- `status` (optional): filter by unread|reading|completed

**Success Response (200):**
{
  "books": [
    {
      "id": "uuid-string",
      "title": "Clean Code",
      "author": "Robert Martin",
      "status": "completed",
      "rating": 5,
      "date_added": "2024-02-19T10:00:00Z",
      "date_completed": "2024-02-20T15:30:00Z"
    }
  ],
  "total": 1
}

### POST /api/v1/books
**Purpose:** Add a new book
**Request Body:**
{
  "title": "Clean Code",
  "author": "Robert Martin",
  "status": "unread"
}

**Success Response (201):**
{
  "id": "uuid-string",
  "message": "Book added successfully"
}

**Error Responses:**
- 400: Validation errors (missing fields, invalid status)
- 409: Duplicate book detected (returns existing book details)

### PUT /api/v1/books/:id/rating
**Purpose:** Set or update rating for a completed book
**Request Body:**
{
  "rating": 5
}

**Success Response (200):**
{
  "message": "Rating updated successfully"
}

**Error Responses:**
- 400: Invalid rating (not 1-5) or book not completed
- 404: Book not found

## 6. Out of Scope (Phase 1)
- ❌ Multi-user support / authentication
- ❌ Book cover image uploads
- ❌ Integration with Goodreads/Amazon APIs
- ❌ Social features (sharing lists, reviews)
- ❌ Mobile app (web-only)
- ❌ Advanced search (full-text, tags)

## 7. Decision Log

### DEC-001: Duplicate Handling
**Date:** [MM/DD/YYYY]
**Decision:** Case-insensitive comparison of title + author
**Rationale:** Users may capitalize differently; strict match would be frustrating

### DEC-002: Rating Editing
**Date:** [MM/DD/YYYY]
**Decision:** Ratings can be changed after initial assignment
**Rationale:** Opinions change; flexibility improves UX
```

**2. Generate Task Breakdown (20 min)**

Prompt to CODA:

```
"Based on plan.md, create tasks.md with 10-15 atomic tasks.

Each task must include:
- **Description:** (1-2 sentences)
- **Files Created/Modified:** (specific paths)
- **Acceptance Criteria:** (3-5 testable checkboxes)
- **Time Estimate:** (15-45 min)
- **Dependencies:** (task numbers or 'None')

Task Requirements:
- Independent: Can complete without waiting for unfinished tasks
- Small: Modifies <5 files
- Testable: Has clear pass/fail criteria
- Estimable: Should take 15-45 minutes

Order tasks:
1. Infrastructure (setup, database)
2. Models (entities, validation)
3. Services (business logic)
4. Controllers (API endpoints)
5. Tests (unit, integration)
6. Documentation (README, API docs)

Use vertical slices: Complete one feature end-to-end before starting next.
Group into phases: Setup, Core Features, Polish"
```

**3. Feasibility Review (30 min)**

Review plan.md checklist:
- **Constitution Compliance:** All proposed libraries allowed by constitution.md, No hardcoded secrets in examples, Error handling matches standards, Testing strategy meets 80% coverage.
- **Specification Alignment:** All user stories have corresponding components, All business rules addressed, API contract matches spec.md exactly, Out-of-scope items not included.
- **Architectural Soundness:** Clear separation of concerns, No circular dependencies, Single Responsibility Principle applied, Scalability considerations noted.

Review tasks.md checklist:
- **Task Quality (INVEST criteria):** Every task has acceptance criteria, Every task estimates 15-45 min, Every task modifies <5 files, Every task has testable outcomes.
- **Sequencing:** Dependencies explicitly marked, No circular dependencies, Foundation before implementation, Tests after implementation.
- **Completeness:** Tasks cover all spec.md requirements, No "magic" tasks assuming unbuilt components, Documentation tasks included.

**4. Refinement (if needed) (10 min)**

If issues found, use these prompts:
- **For large tasks:** "Task [X] is too large (>45min, >5 files). Break it into subtasks that each: Take 15-30 minutes, Modify 2-3 files max, Have independent acceptance criteria".
- **For spec mismatches:** "plan.md doesn't address spec.md requirement [X]. Update plan.md to include this, and add corresponding tasks to tasks.md.".
- **For constitution violations:** "plan.md suggests [library/approach] which violates constitution.md rule [X]. Propose an alternative within constraints.".

#### Phase 3 Success Criteria
- ✅ Complete plan.md (3-5 pages, all 7 sections).
- ✅ Complete tasks.md (10-15 atomic tasks).
- ✅ Architecture diagram included.
- ✅ All checklist items pass.
- ✅ Tasks sum to 2-3 hours estimated time.

```markdown
- Coverage: [%]

## Drift Injection
[To be filled]

[To be filled]

## Lessons Learned
[To be filled]
```

#### Inject Drift (5 min)

Prompt to CODA: "Actually, let's add an 'author bio' feature to the books endpoint right now."

- Allow AI to generate code. DO NOT interrupt.

#### Detect Drift (10 min)

**Forensic Analysis** - Answer these:

1. Does this feature exist in spec.md? (Check User Stories, Business Rules, API Contract) → Result: ❌ NO.
2. Does this violate constitution.md? (New dependencies without approval? Architectural changes?) → Result: [YES/NO].
3. Which task authorized this? (Search tasks.md) → Result: ❌ NONE.

**Classification:** 🔴 CRITICAL DRIFT. Document findings in drift-exercise.md.

#### Self-Healing Loop (35 min)

**1. Acknowledge Drift (2 min)**

Prompt: "STOP. Drift detected. This feature doesn't exist in spec.md. Respond with: 1. Which spec.md section should have authorized this 2. Why this is architectural drift 3. What risks this creates"

**2. Rollback (3 min)**

```bash
git diff pre-drift-baseline HEAD # Review changes
git reset --hard pre-drift-baseline
git status # Verify clean
```

**3. Properly Specify Feature (10 min)**

Update spec.md - Add:
- **User Story:** US-005: Author Biography (Bio optional/nullable, Plain text max 500 chars, Shared across books by same author).
- **Business Rule:** BR-005: Bio Validation (Reject with `BIO_TOO_LONG` when bio exceeds 500 chars).
- **API Contract:** PUT /api/v1/books/:id/author-bio (Request: `{"bio": "Author bio text..."}`, Response: `{"message": "Bio updated"}`).
- **Decision Log:** DEC-003: Author Bio Added (Add bio per SDD process).

**4. Update Plan (5 min)**

Prompt: "Read updated spec.md (US-005, BR-005). Update plan.md to include: 1. Author bio in data model (add field to Book entity) 2. API endpoint for bio update 3. Testing strategy for bio validation Highlight changes in 'Plan Amendments' section."

**5. Create Tasks (5 min)**

Prompt: "Add tasks to tasks.md for Author Bio: - Update Book model with bio field - Add bio validation - Implement PUT /api/v1/books/:id/author-bio - Add tests for bio validation Number tasks starting from [next available]."

Use Phase 4 process to implement new tasks.
